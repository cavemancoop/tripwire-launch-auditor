## 3. Architecture decisions made this session (critique these)

### 3.1 Benchmark transport: shared file → Postgres row
M7 shipped "fork-and-run: one filesystem, no network hop" — the worker writes
`data/benchmark.json`, the API reads it. That is structurally impossible on
Railway: api and worker are separate containers with separate filesystems and no
shared volume. Added a `BenchmarkSnapshot` singleton row; `GET /v1/benchmark`
reads Postgres by default, the file write stays for local debugging.

*Concern I have:* this puts a ~100KB JSON blob through Postgres, rewritten every
5 minutes, purely as an IPC channel. It works and Postgres is the one thing every
topology already shares — but is it the right transport, or should the API just
compute the benchmark itself (it already has Prisma and the scoring package), or
should this be object storage / Redis?

### 3.2 Migrations from the worker container's entrypoint
Railway's Postgres is private-network-only. Neither a direct connection from the
laptop nor `railway run` could reach `postgres.railway.internal` (both P1001).
The worker container is inside that network, so its `CMD` now runs
`prisma migrate deploy` before `exec`ing the app. Idempotent, so safe on every
restart.

*Concern:* it couples schema migration to worker startup. With >1 replica this
races (Prisma takes an advisory lock, so probably survives, but it's not a
designed-for-concurrency path). Is there a better Railway-native pattern — a
one-off job, a release command — that I missed?

### 3.3 Dual-scope benchmark instead of teaching the scorer about retrospective rows
The dashboard needs a "retrospective" badge per cell. Rather than change
`packages/scoring` to tag rows, the snapshot loop runs `runScorer` twice
(`scope: 'both'` and `scope: 'live'`) and ships both; the dashboard diffs a
cell's `n` between them to derive "+N retro."

*Concern:* double the scoring compute every 5 minutes to avoid touching a
package. On the current data that's cheap. Is this a reasonable trade or a
shortcut that should be paid down before it grows?

### 3.4 Dropped the `web_search` server tool
Every real deep-dive was failing with `ResponseValidationError: Response
validation failed`. Bisected against the SDK directly: a plain call to
`deepseek/deepseek-v4.1-flash` through the Orbio gateway works; the same call
*with structured output* works; adding `DEEPDIVE_SERVER_TOOLS`
(`web_search_2025_08_26`) fails every time. Underlying cause is a shape
mismatch — the gateway returns an error envelope whose `error.code` is a
**string** where the pinned `@openrouter/sdk` zod schema expects a **number**, so
the SDK throws before Orbio's actual error text is ever visible. Removed from the
live tool set; the constant is kept so restoring it is one line.

*Concern:* spec §6's tool belt explicitly includes web_search. We're now one
evidence source short and I documented it as a gateway limitation. Is that the
right call, or is this worth working around (patch the SDK, catch-and-retry
without the tool, or raise it with Orbio as an upstream bug)? It looks like a
genuine Orbio-side spec violation rather than our bug.

### 3.5 Forward-window clamping inside `pickPrimaryV4Pool`
**This was a real, silent, 2-day production bug.** The primary-pool
re-derivation scans *forward* from the launch block: +2h for the Initialize scan,
+10m for activity. At chain 4663's 0.1s blocks that's a **72,000-block** window,
so on a fresh launch roughly seven of its eight 9,999-block chunks ask for blocks
that don't exist yet. Blockmachine (local) clamped that silently. Chainstack
(production) rejects it with `invalid block range params`, which threw, which the
`try/catch` in `t10.ts` swallowed as a warning — so **M4's decoy/side-pool
correction never ran on a single production launch**. Every launch kept whatever
pool the watcher first latched onto, including the >10%-fee decoys
`poolFeeSuspect` exists to catch, and that feeds liquidity, sell-impact and
outcome resolution.

Isolated by direct probing of the Chainstack endpoint: a window *ending* past
head is tolerated (clamped), one *starting* past head is rejected; the span limit
is a separate 10,000 with its own clearer error; the `null` topic slot is fine.

Clamped inside `pickPrimaryV4Pool` (covers both callers — `t10` and `backfill`)
rather than at each call site or inside `getLogsChunked`. Two regression tests
pin that no query asks for blocks past head. Confirmed fixed in production after
redeploy: zero failures, and the first real switch logged
(`2 candidate(s)`, `swaps10m=118`).

*Concern:* is `pickPrimaryV4Pool` the right layer? `getLogsChunked` is the
primitive that actually builds the offending request, but it's in
`packages/chain` and has no notion of head. I chose the caller that owns the
semantics ("scan forward from launch") over the primitive.

*Also worth noting:* each failure was burning 3 retries × 8 chunks × 2s of RPC
budget per launch, at ~3,200 launches/day. The `withRetry` wrapper made a
permanent failure expensive.

### 3.6 Smaller calls
- **CORS wildcard** on the API — every endpoint is public read or free-during-contest write, no cookies, nothing origin-scoped.
- **Container `CMD` invokes `tsx`/`node` directly**, not `pnpm --filter … start`: pnpm's dependency-status check wants a TTY and aborts on *every container start*, not just at build.
- **`.dockerignore` added** — without it `COPY . .` overwrote the image's Linux `node_modules` with Windows binaries. Caught by actually running the built image, not by reading it.
- **Worker health port is `WORKER_PORT` (3010), deliberately not `$PORT`** — this repo's `.env` sets `PORT=3000` for the api and both processes read the same file locally, so a bare `$PORT` fallback collided.

## 4. The three claim-level findings

These are the ones I think matter most for the submission.

### 4.1 Spec §0.1 property 2 is not implemented
Property 2 is *"the daily deep-dive budget is a function of credits accrued in
the trailing 24h; throughput visibly follows token activity and holdings."*

`apps/worker/src/metabolism/budget.ts` contains `dailyDeepdiveBudget()`, which
implements exactly the spec's three-term min — `min(dailyCapUsd, 0.5 ×
trailingCreditsUsd, keyRemaining − reserve)` — with a `bindingConstraint` field
and tests. **It is never called anywhere outside tests.** The live gate,
`deepdiveRunGate()`, takes `capPerRunUsd`, `dailyCapUsd`, today's spend,
spendable balance and billing status. There is **no accrual term in the live
path at all**.

So the property that most distinguishes this from a plain OpenRouter account is
currently a function that exists and is unused.

**Proposed fix (~40 lines):** the data already exists. The lifecycle log snapshots
`balanceUsd` every 60s; credits accrued over a window = the sum of *positive*
deltas between consecutive snapshots. I already implemented exactly this
derivation client-side for the dashboard's "credits accrued/hr" metric. Move it
server-side into `defaultLoadBudget`, pass `trailingCreditsUsd`, and have the
gate use the three-term min. The dashboard already surfaces `bindingConstraint`,
so when it reads `credit_share` the property is visible, live, on screen.

### 4.2 Orbio is absent from the deployed instance
The OAuth token store is a local encrypted file (`.orbio/token-store.enc.json`,
gitignored, never deployed). Railway's worker has its own empty filesystem and
has never run the interactive flow. Compounding it: we measured earlier that
Orbio's refresh grant is **one-shot** (first use returns 200 with no replacement
refresh token; any reuse is 400 `invalid_grant`), so a session is bounded by the
**~1h access-token lifetime**.

Consequences on the deployed instance: no key claimed, zero lifecycle rows, zero
deep-dives, zero spend, both P&L boxes at $0.00, Metabolism panel all `n/a`.
Properties 1 and 3 are undemonstrable there.

Options I see, roughly by robustness:
1. Expose the worker's OAuth callback port publicly on Railway + a volume so the token survives redeploys; run the browser flow against the deployed container. Still needs re-auth ~hourly.
2. Seed the token via env var (base64 the local encrypted store, write it out on boot). Trivial, but only useful if done immediately before judging.
3. Run the metabolism instance locally during judging and be explicit about it.

The project's existing stance — *"unattended continuity is bounded by the access
token's lifetime; that bound is the number to publish, not something to hide"* —
is honest and I think it's the strongest asset here. **This is the decision I
most want your read on.**

### 4.3 Local and production hold disjoint, non-overlapping datasets
- **Local**: ~14,000 scored rows, **100% retrospective** (the backfill), `live n=0`.
- **Production**: 1,602 scored rows, **100% live**, precommitted and on-chain, zero backfill.

Production's is the honest dataset and it's the one a judge sees, but the base
rates that cost days of RPC budget aren't in it. Merge the backfill into
production, or present them as two explicitly-labelled datasets on the dashboard?
Production is currently accruing ~200–300 resolved outcomes per cell per day, so
letting it run 3–4 more days clears the claim bar on genuinely live data.

## 6. What I want feedback on

1. **§4.2, the Orbio continuity problem.** Given a ~1h token, a one-shot refresh and an interactive browser flow — is there a deployment pattern that yields genuinely unattended operation, or is "publish the bound" the right and final answer? This is the crux of property 3.
2. **§4.1, the property-2 fix.** Is an accrual figure *derived from positive deltas in our own balance snapshots* honest enough to claim "credit-driven behavior," or does that claim require a first-class accrual number from Orbio that we don't currently have a tool for?
3. **§4.3, backfill vs live.** Merge the retrospective data into production, or two labelled datasets? Which makes the stronger and more honest submission?
4. **Is the demo proving the right thing at all?** Most of what's deployed and healthy — watcher, features, commits, outcomes, scorer, dashboard — passes the "would work identically on plain OpenRouter" test, i.e. proves nothing Orbio-specific. My proposed priority order is: dashboard API-URL fix → Telegram vars → wire property 2 → Orbio auth on Railway → let it run → M10. Is that right, or is something else higher leverage with ~days left?
5. **The §3 decisions** — particularly 3.1 (Postgres as IPC), 3.2 (migrations at container start) and 3.4 (dropping web_search). Any of those accumulating avoidable complexity or debt?
6. **Anything the audit missed.** I checked what I could reach; I'd rather you find a seventh thing now than a judge find it later.
